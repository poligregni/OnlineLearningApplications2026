# Requirement 2 — Multiple Campaigns, Stochastic Environment

This notebook continues directly from `requirement1_single_campaign.ipynb`. It keeps the same guided, heavily-commented style: every code cell is preceded by a short paragraph explaining *what we are about to do and why*, and followed by a short paragraph explaining *how to read the result*.

### What Requirement 2 asks for

Recall from `project.pdf`: the agency doesn't run just one campaign — it runs $N$ advertising campaigns **at the same time**, sharing a **single budget** $B$ over the whole horizon $T$. Two new ingredients appear compared to Requirement 1:

1. **Multiple campaigns, still stochastic**: build a **joint distribution over the highest competing bids** $(m_{1,t}, \dots, m_{N,t})$ for the $N$ campaigns (instead of just one $m_t$).
2. **Non-compatible campaigns**: recall the general project constraint (slide 7 of `project.pdf`) — some pairs of campaigns are direct competitors (e.g. Coca-Cola and Pepsi) and **cannot be bid on in the same round**. This is encoded as a *conflict graph* over the $N$ campaigns: an edge means "these two campaigns can never both be active in the same round." For a single campaign ($N=1$, Requirement 1) this constraint is empty and invisible; here, with $N>1$, it becomes a real part of the decision problem.

The algorithm we must build is:

> Build a bidding strategy using **Combinatorial-UCB** with the **budget constraint**, by extending the "UCB-like" approach we saw for a single campaign (Algorithm 2 of Requirement 1) to multiple campaigns.

So there is only **one** algorithm to design here (no "ignore the budget" baseline this time — Requirement 1 already made the case for why budgets matter). The whole notebook builds towards that single agent.

### The rules of the game (recap, now with $N$ campaigns)

At every round $t$:

1. For every campaign $i \in \{1, \dots, N\}$ we may choose a bid $b_{i,t}$ from the same small discrete set $\mathcal{B}$ — **or** skip campaign $i$ this round.
2. **Skipping is forced, not optional, for conflicting campaigns**: if campaigns $i$ and $j$ conflict, at most one of them may be active (bid on) in round $t$.
3. For each *active* campaign, a first-price auction is run against a highest competing bid $m_{i,t}$ drawn i.i.d. from campaign $i$'s own distribution.
4. Winning campaign $i$ this round earns utility $f_{i,t} = (v_i - b_{i,t})$ and costs $c_{i,t} = b_{i,t}$; skipped or lost campaigns contribute $0$ to both.
5. **One** budget $B$ is shared across *all* campaigns and the *entire* horizon $T$: every payment, from any campaign, is subtracted from the same pool.

This is exactly the single-campaign game of Requirement 1, played $N$ times in parallel, with two twists layered on top: a compatibility constraint on which subset of campaigns can play each round, and one shared purse instead of $N$ separate ones.

        pass

class FirstPriceAuction(Auction):
    def __init__(self, qs):
        self.qs = qs
        self.n_adv = len(self.qs)

    def get_winners(self, bids):
        public_values = self.qs * bids
        public_ranking = np.argsort(public_values)
        winner = public_ranking[-1]
        return winner

    def get_payments_per_click(self, winners, bids):
        payment = bids[winners]
        return payment

## 2. The new ingredient: non-compatible campaigns

### The conflict graph

Before building the environment, we need a way to describe *which* campaigns can never be bid on together. We represent this as an undirected graph $G=(V,E)$ with one node per campaign; an edge $(i,j)$ means campaigns $i$ and $j$ are direct competitors (project.pdf's own example: Coca-Cola and Pepsi) and can never both be active in the same round.

A round's decision is therefore not "pick any subset of campaigns" — it's "pick an **independent set** of $G$" (a set of nodes with no edge between any two of them), and then a bid for each campaign in that set. `enumerate_independent_sets` below just brute-forces this: for small $N$ (a handful of campaigns, as the project intends), the number of independent sets is small enough to list explicitly rather than solve implicitly at every round.
===== CELL 8 [code] =====
def enumerate_independent_sets(N, edges):
    '''All subsets of {0, ..., N-1} that contain no edge from `edges`
    (including the empty set: 'bid on nothing this round' is always feasible).'''
    def is_independent(subset, edges):
        subset_set = set(subset)
        return all(not (i in subset_set and j in subset_set) for (i, j) in edges)

    independent_sets = []
    for r in range(N + 1):
        for combo in itertools.combinations(range(N), r):
            if is_independent(combo, edges):
                independent_sets.append(combo)
    return independent_sets

## 3. The stochastic environment for multiple campaigns

### What we're building here

The project asks for "a joint distribution over the highest competing bids for each campaign." The simplest valid joint distribution is the **product** of $N$ independent per-campaign distributions — each campaign's competition is exactly as in Requirement 1 (a $\mathrm{Beta}(n_i, 1)$, as if $n_i$ rival bidders bid uniformly at random in campaign $i$'s own auction), but now every campaign gets its own value $n_i$ (different markets attract different amounts of competition). This is a legitimate joint distribution (independence is a special case of joint dependence), and it keeps the per-campaign clairvoyant benchmarks computable in closed form, exactly like Requirement 1. *(A natural, more realistic extension — left for future work — would tie the campaigns together with a shared "macro" shock, e.g. all competitors bid a bit more aggressively on days with high overall ad demand; nothing below depends on that extra structure, so it can be bolted on later without changing the algorithm.)*

`MultiCampaignEnvironment` below is the direct multi-campaign generalization of Requirement 1's `SingleCampaignEnvironment`: instead of one scalar $m_t$ per round, it stores an $N \times T$ table, one row per campaign. Its `round` method takes a length-$N$ vector of bids where **`np.nan` marks a campaign that isn't bid on this round** (because it was skipped due to the conflict graph, or because the budget ran out) — and returns the vector of per-campaign utilities, costs, and wins, with zeros in the skipped positions.
===== CELL 16 [code] =====
class MultiCampaignEnvironment:
    # Stochastic environment for Requirement 2: N campaigns, each with its own
    # first-price auction, where m_{i,t} ~ m_distributions[i] i.i.d. over t.
    # Together, the N (independent) per-campaign distributions form the joint
    # distribution over the highest competing bids the project asks for.
    def __init__(self, valuations, m_distributions, T, seed=None):
        self.valuations = np.asarray(valuations, dtype=float)
        self.N = len(self.valuations)
        self.T = T
        rng = np.random.default_rng(seed)
        self.m_t = np.array([dist.rvs(size=T, random_state=rng) for dist in m_distributions])  # N x T
        self.t = 0

    def round(self, bids):
        # bids: length-N array; np.nan marks a campaign that is not bid on this round.
        bids = np.asarray(bids, dtype=float)
        active = ~np.isnan(bids)
        win = np.zeros(self.N)
        win[active] = (bids[active] >= self.m_t[active, self.t]).astype(float)
        f_t = np.zeros(self.N)
        c_t = np.zeros(self.N)
        f_t[active] = (self.valuations[active] - bids[active]) * win[active]
        c_t[active] = bids[active] * win[active]
        self.t += 1
        return f_t, c_t, win

## 4. From single bids to super-arms: the combinatorial action space

### Why this is the crux of "Combinatorial"-UCB

In Requirement 1 the agent chose **one** action per round: a single bid $b \in \mathcal{B}$, i.e. one of $K=11$ arms. Here, a round's action is "a bid for every campaign in some independent set" — an entire *combination* of (campaign, bid) pairs. Following exactly the recipe from the course's combinatorial-bandits session (`09_combinatorial_mabs.ipynb`, "Combinatorial UCB": *build a UCB for each arm, the UCB of a super-arm is the sum of the UCBs of its components, play the super-arm with the highest (budget-feasible) UCB*), we:

1. Treat every **(campaign $i$, bid $b$)** pair as its own elementary arm — there are $N \times K$ of them.
2. Enumerate every **super-arm**: a choice of one elementary arm for each campaign in some independent set $S$ (plus the special "empty" super-arm: bid on nothing). For $N=4$ campaigns, $K=6$ bids, and the one Cola/Soda conflict above, this works out to a few hundred super-arms — still small enough to enumerate explicitly and hand to `scipy.optimize.linprog` as we did for the single bid set in Requirement 1.
3. Build a sparse 0/1 "membership matrix" $M$ (super-arms $\times$ elementary arms) so that, given a vector of per-arm UCB/LCB values, we can compute *every* super-arm's combined UCB/LCB with one matrix-vector product, instead of a slow Python loop over hundreds of super-arms at every one of the $5000$ rounds.

This is the *only* conceptual change from Requirement 1's Algorithm 2 — the LP itself, a few cells below, has exactly the same shape as before (maximize expected reward subject to expected cost $\le \rho$ over a probability simplex); the simplex is just now over super-arms instead of over single bids.
===== CELL 24 [code] =====
def build_super_arms(independent_sets, K):
    '''Every feasible combination of (campaign, bid) pairs: one bid choice
    per campaign in an independent set (plus the empty super-arm).'''
    super_arms = []
    for S in independent_sets:
        if len(S) == 0:
            super_arms.append(())
            continue
        for bid_combo in itertools.product(range(K), repeat=len(S)):
            super_arms.append(tuple(zip(S, bid_combo)))
    return super_arms


def build_membership_matrix(super_arms, N, K):
    '''Sparse (n_super_arms x N*K) 0/1 matrix: row a, column i*K+b is 1 iff
    super-arm a bids b on campaign i. Lets us compute every super-arm's total
    UCB/LCB via one sparse matrix-vector product per round.'''
    rows, cols = [], []
    for a_idx, arm in enumerate(super_arms):
        for (i, b) in arm:
            rows.append(a_idx)
            cols.append(i * K + b)
    data = np.ones(len(rows))
    return sparse.csr_matrix((data, (rows, cols)), shape=(len(super_arms), N * K))


super_arms = build_super_arms(independent_sets, K)
M = build_membership_matrix(super_arms, N, K)
n_super_arms = len(super_arms)
print(f'Number of elementary (campaign, bid) arms: {N * K}')
print(f'Number of feasible super-arms: {n_super_arms}')

## 5. The clairvoyant benchmark $\mathrm{OPT}^S$

Exactly as in Requirement 1, the right yardstick for a budget-constrained algorithm is: *"the best possible way of randomly mixing between feasible actions, if we had known the true win-probabilities in advance, that still respects the (shared) budget on average."* The only difference is that "feasible actions" now means *super-arms* instead of single bids:

$$ \mathrm{OPT}^S = \max_{\gamma \in \Delta(\text{super-arms})} \sum_{\text{arm}} \gamma(\text{arm})\, \bar F(\text{arm}) \quad \text{s.t.} \quad \sum_{\text{arm}} \gamma(\text{arm})\, \bar C(\text{arm}) \le \rho, $$

where $\bar F(\text{arm}) = \sum_{(i,b) \in \text{arm}} \bar f_i(b)$ and $\bar C(\text{arm}) = \sum_{(i,b) \in \text{arm}} \bar c_i(b)$ are just the sums, over the (campaign, bid) pairs in that super-arm, of each campaign's own expected utility $\bar f_i(b) = (v_i - b)\,\mathbb{P}(b \ge m_i)$ and expected cost $\bar c_i(b) = b\,\mathbb{P}(b \ge m_i)$ — precisely the quantities computed in Requirement 1, now just summed across whichever campaigns a super-arm activates. This is still a plain linear program over a probability simplex, solved once with `scipy.optimize.linprog`.
===== CELL 27 [code] =====
def compute_clairvoyant_combinatorial(super_arms, M, valuations, available_bids, win_probabilities, rho):
    N, K = win_probabilities.shape
    f_bar = (valuations[:, None] - available_bids[None, :]) * win_probabilities   # N x K
    c_bar = available_bids[None, :] * win_probabilities                          # N x K
    F_arm = M.dot(f_bar.flatten())   # expected utility of every super-arm
    C_arm = M.dot(c_bar.flatten())   # expected cost of every super-arm
    n_arms = len(super_arms)
    res = optimize.linprog(-F_arm, A_ub=[C_arm], b_ub=[rho],
                            A_eq=[np.ones(n_arms)], b_eq=[1], bounds=(0, 1))
    gamma = np.clip(res.x, 0, None)
    gamma = gamma / gamma.sum()
    return gamma, F_arm @ gamma, C_arm @ gamma, F_arm, C_arm


gamma_clairvoyant, expected_clairvoyant_utility, expected_clairvoyant_payment, F_arm_true, C_arm_true = \
    compute_clairvoyant_combinatorial(super_arms, M, valuations, available_bids, win_probabilities, rho)

support = np.where(gamma_clairvoyant > 1e-6)[0]

**Reading the output**: the optimal (budget-respecting) mixture ends up randomizing between just a couple of super-arms, and — this is worth pausing on — it **never activates Cola**, even though Cola is (on its own) a perfectly profitable campaign. The reason is the conflict graph: since Cola and Soda can never both play, the LP only ever gets to pick *one* of them, and it picks Soda every time. This is *not* simply "Soda has the higher valuation" (it doesn't — $0.5 < 0.6$) or "Soda's own best fixed bid is more efficient bid-for-bid" (a naive per-bid efficiency check is actually misleading here, since it doesn't account for how the campaigns interact through the shared budget). What actually drives it is that Soda faces *weaker* competition ($n=2$ rival bidders vs. Cola's $n=3$), so a cheap bid already wins a good share of Soda's auctions — enough that, once you compare the two campaigns like-for-like at the budget level (not bid-for-bid), swapping the Soda-based super-arms for their Cola-based counterparts strictly *reduces* total expected reward at the same cost (you can check this by comparing `arm_val` for e.g. `(Soda, Sneakers, Coffee)` vs. `(Cola, Sneakers, Coffee)` at matching bids). This is exactly the kind of "detailed discussion of unexpected results" `project.pdf` invites for the final presentation: it's the *combinatorial*, budget-level interaction between campaigns — not either campaign's numbers in isolation — that decides the outcome, and Section 6 below shows the *learning* agent doesn't actually manage to discover this same preference in time.

## 6. Combinatorial-UCB with a shared budget constraint

### The idea in plain words — a direct extension of Requirement 1's Algorithm 2

This is the "UCB-like" agent Requirement 1 built, extended exactly as `project.pdf` hints:

- For **every elementary arm** (campaign $i$, bid $b$) — there are $N \times K$ of them — keep the same optimistic reward estimate and the same *pessimistic* (lower-bound) cost estimate as before:
$$ \bar f_t^{\text{UCB}}(i,b) = \bar f_t(i,b) + \sqrt{\frac{2\log T}{N_{t-1}(i,b)}}, \qquad \bar c_t^{\text{LCB}}(i,b) = \bar c_t(i,b) - \sqrt{\frac{2\log T}{N_{t-1}(i,b)}}. $$
- For **every super-arm**, sum the UCBs/LCBs of its components — this is the textbook Combinatorial-UCB rule ("the UCB of a super-arm is the sum of the UCBs of its arms").
- Solve **one** linear program per round — same shape as Requirement 1's, just over super-arms instead of single bids:
$$ \gamma_t = \arg\max_{\gamma \in \Delta(\text{super-arms})} \sum_{\text{arm}} \gamma(\text{arm})\, F_t^{\text{UCB}}(\text{arm}) \quad \text{s.t.} \quad \sum_{\text{arm}} \gamma(\text{arm})\, C_t^{\text{LCB}}(\text{arm}) \le \rho. $$
- Draw the actual round's action $\text{arm}_t \sim \gamma_t$ — this automatically respects the conflict graph (every super-arm in the simplex is feasible by construction) and paces spending against the *one shared* budget.
- Update the running averages **only** for the (campaign, bid) pairs that were actually part of $\text{arm}_t$ — semi-bandit feedback, exactly as the environment's `round` method returns zeros for every campaign that wasn't bid on.
- Once the shared budget is (nearly) exhausted, stop bidding on everything, exactly as Requirement 1's Algorithm 2 does.

One bookkeeping detail carried over from Requirement 1: the very first rounds are used to guarantee every one of the $N \times K$ elementary arms is tried **at least once**, so the running averages are never divided by zero. We do this via the always-feasible *singleton* super-arms (bid on exactly one campaign, one specific untried bid, and nothing else) — a direct generalization of "try each of the $K$ bids once" from Requirement 1.
===== CELL 30 [code] =====
class CombinatorialUCBBiddingAgent:
    def __init__(self, super_arms, M, N, K, B, T, reward_range=1):
        self.super_arms = super_arms
        self.M = M
        self.N = N
        self.K = K
        self.n_arms = len(super_arms)
        self.T = T
        self.range = reward_range
        self.budget = B
        self.rho = B / T
        self.avg_f = np.zeros(N * K)   # running average reward, per elementary (campaign, bid) arm
        self.avg_c = np.zeros(N * K)   # running average cost, per elementary (campaign, bid) arm
        self.N_pulls = np.zeros(N * K)
        # round-robin schedule guaranteeing every elementary arm is tried once,
        # via the always-feasible singleton super-arm ((campaign, bid),)
        self.init_schedule = [((i, b),) for i in range(N) for b in range(K)]
        self.t = 0
        self.chosen_arm = None

    def bid(self):
        if self.budget < 1:
            self.chosen_arm = ()  # budget exhausted: bid on nothing, for the rest of the horizon
            return self.chosen_arm
        if self.t < len(self.init_schedule):
            self.chosen_arm = self.init_schedule[self.t]
            return self.chosen_arm
        f_ucbs = self.avg_f + self.range * np.sqrt(2 * np.log(self.T) / self.N_pulls)
        c_lcbs = self.avg_c - self.range * np.sqrt(2 * np.log(self.T) / self.N_pulls)
        F_arm = self.M.dot(f_ucbs)
        C_arm = self.M.dot(c_lcbs)
        gamma_t = self._solve_lp(F_arm, C_arm)
        arm_idx = np.random.choice(self.n_arms, p=gamma_t)
        self.chosen_arm = self.super_arms[arm_idx]
        return self.chosen_arm

    def _solve_lp(self, F_arm, C_arm):
        # if no super-arm can possibly satisfy the (optimistic) budget constraint,
        # just play the single-round-optimal super-arm
        if np.all(C_arm > self.rho):
            gamma = np.zeros(self.n_arms)
            gamma[np.argmax(F_arm)] = 1.0
            return gamma
        res = optimize.linprog(-F_arm, A_ub=[C_arm], b_ub=[self.rho],
                                A_eq=[np.ones(self.n_arms)], b_eq=[1], bounds=(0, 1))
        gamma = np.clip(res.x, 0, None)
        total = gamma.sum()
        if total <= 0:
            gamma = np.zeros(self.n_arms)
            gamma[np.argmax(F_arm)] = 1.0
            return gamma
        return gamma / total

    def update(self, f_t, c_t):
        # semi-bandit feedback: only refine estimates for arms in the played super-arm
        total_cost = 0.0
        for (i, b) in self.chosen_arm:
            idx = i * self.K + b
            self.N_pulls[idx] += 1
            self.avg_f[idx] += (f_t[i] - self.avg_f[idx]) / self.N_pulls[idx]
            self.avg_c[idx] += (c_t[i] - self.avg_c[idx]) / self.N_pulls[idx]
            total_cost += c_t[i]
        self.budget -= total_cost
        self.t += 1


def arm_to_bids_vector(arm, N, available_bids):
    bids = np.full(N, np.nan)
    for (i, b) in arm:
        bids[i] = available_bids[b]
    return bids

===== CELL 31 [markdown] =====
**What this class does, step by step**: `bid()` first checks the shared budget; while it's healthy, the first $N \times K = 24$ calls just work through the round-robin schedule (one elementary arm at a time), and afterwards every call computes UCB/LCB values for all $24$ elementary arms, sums them into UCB/LCB values for all $637$ super-arms via the sparse matrix $M$, solves the LP, and samples a super-arm. `update()` is handed the *full* length-$N$ utility/cost vectors from the environment (with zeros in every campaign that wasn't played) but only touches the entries for campaigns that were actually in `chosen_arm` — exactly the semi-bandit rule. `arm_to_bids_vector` is a small helper translating an agent's abstract "super-arm" (a set of (campaign-index, bid-index) pairs) into the length-$N$, `nan`-marked bids vector the environment's `round` method expects. Nothing is simulated yet — we run it below.

### Running the experiment

Same idea as Requirement 1: repeat the whole $T=5000$-round experiment over several random seeds and average, tracking, for every trial, the cumulative regret against $\mathrm{OPT}^S$, the cumulative shared spending, how often every (campaign, bid) pair was played, and the round at which the shared budget first drops below $1$.

$$ \text{Regret}(T) = \sum_{t=1}^{T} \big(\mathrm{OPT}^S - (f_{1,t} + \dots + f_{N,t})\big) $$

Solving a $637$-variable LP is of course heavier than Requirement 1's $11$-variable one, but because our shared budget is tight relative to four campaigns' worth of spending, the budget is typically exhausted well before $T$ — after that point `bid()` returns the empty super-arm immediately, without touching the LP at all, which keeps the whole experiment fast despite the larger action space.

for seed in range(n_trials):
    env = MultiCampaignEnvironment(valuations, m_distributions, T, seed=seed)
    agent = CombinatorialUCBBiddingAgent(super_arms, M, N, K, B, T)

    utilities = np.zeros(T)
    costs = np.zeros(T)
    depletion_round = None

    for t in range(T):
        arm = agent.bid()
        bids = arm_to_bids_vector(arm, N, available_bids)
        f_t, c_t, win = env.round(bids)
        agent.update(f_t, c_t)
        utilities[t] = f_t.sum()
        costs[t] = c_t.sum()
        if depletion_round is None and agent.budget < 1:
            depletion_round = t

    cumulative_regret = np.cumsum(expected_clairvoyant_utility - utilities)
    regret_per_trial.append(cumulative_regret)
    payments_per_trial.append(np.cumsum(costs))
    pulls_per_trial.append(agent.N_pulls.copy())
    depletion_round_per_trial.append(depletion_round if depletion_round is not None else T)

## 7. Concluding remarks

1. **The same "UCB-like" recipe scales up cleanly**: nothing about the core idea changed going from $1$ campaign to $N=4$ — still an upper confidence bound on reward, a lower confidence bound on cost, and one linear program solved per round over a probability simplex. The only new work was combinatorial bookkeeping: enumerating feasible super-arms once (Section 4) and letting a sparse matrix multiplication turn per-arm UCB/LCB values into per-super-arm ones every round.
2. **The conflict graph is resolved for free by the LP — but only for the *clairvoyant*, not (yet) for the learner**: because every super-arm in the LP's simplex is, by construction, a *feasible* (independent-set-respecting) combination, neither the clairvoyant nor the agent ever has to separately reason about "is this legal?" — legality is baked into which columns exist in the first place. With perfect knowledge (Section 5), this correctly identifies that, of the two mutually-exclusive campaigns, only Soda is worth activating. But Section 6's bid-distribution plot shows the *learning* agent does not reproduce that clean preference — it ends up splitting its plays almost evenly between Cola and Soda. That gap between the clairvoyant's answer and the learner's behavior is itself informative: it's a direct symptom of point 3 below (the budget runs out before there's enough data to tell the two campaigns apart), not a flaw in how the combinatorial constraint is handled.
3. **Sharing one budget across campaigns changes the depletion story, not the learning guarantee — but a fast depletion can starve the learning itself**: exactly as in Requirement 1, this budget-aware agent's cumulative regret is concave (sublinear) for as long as money remains, then turns into an exactly straight line the moment the shared pool empties — here that happens far earlier ($\approx 8\%$ of the horizon) than in Requirement 1's single-campaign example ($\approx 60\%$), simply because four campaigns draw on the same pool of money instead of one. The practical consequence is exactly the "unexpected result" flagged in Section 6: with only a few hundred rounds of real learning before the money runs out, the agent doesn't get the chance to fully resolve which of two competing campaigns is actually better — a longer horizon (or a proportionally larger budget) would be expected to close that gap, since the theory behind Combinatorial-UCB still guarantees convergence, just not necessarily within this particular, budget-shortened window.
4. **What comes next (Requirement 3)**: the environment and conflict graph built here carry over unchanged; what changes is the *competition* — instead of one fixed (if unknown) distribution per campaign, Requirement 3 asks for a highly non-stationary sequence of competing bids, tackled with a primal-dual method (a full-feedback, best-of-both-worlds algorithm) rather than the stochastic-only Combinatorial-UCB built here.
